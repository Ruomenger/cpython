# 00. 编译配置

记录在本地把 CPython 3.11 配置成「树外调试构建」的完整过程,用于源码学习与断点调试。

## 目标

- **out-of-tree(树外)编译**:所有产物落在 `build/` 目录,源码树保持干净。
- **调试构建**:`--with-pydebug` + `OPT="-g -O0 -Wall"`,带调试符号、**零优化**、开启断言与引用计数追踪,确保断点调试时变量可见、单步不跳行。
- **生成 `compile_commands.json`**:供 clangd / IDE 做代码跳转与补全。

## 环境

- macOS(Apple Silicon)
- 源码位于**大小写敏感卷**(`/Volumes/Dev/...`),所以解释器二进制叫 `python`,而非大小写不敏感卷上的 `python.exe`(后者是为了避免与源码里的 `Python/` 目录冲突)。
- 依赖工具:Homebrew、`bear`、Xcode Command Line Tools。
- 参考 CI 配置:`.github/workflows/reusable-macos.yml` 与 `Misc/Brewfile`。

## 1. 安装依赖

依赖清单直接复用仓库自带的 `Misc/Brewfile`(和 macOS CI 一致):

```bash
brew bundle --file=Misc/Brewfile
# 下面 configure 时通过 PKG_CONFIG_PATH 选择 tcl-tk@8,
# 无需修改 Homebrew 的全局链接。
```

`Misc/Brewfile` 在 macOS 上包含:`gdbm`、`mpdecimal`、`openssl@3.0`、`pkg-config`、`tcl-tk@8`、`xz`、`zstd`。

## 2. 在 build/ 目录里 configure

```bash
mkdir -p build && cd build

export CC=clang   # 关键:用 PATH 里的 Homebrew LLVM clang,不要用 /usr/bin/clang

PKG_CONFIG_PATH="$(brew --prefix tcl-tk@8)/lib/pkgconfig${PKG_CONFIG_PATH:+:$PKG_CONFIG_PATH}" \
GDBM_CFLAGS="-I$(brew --prefix gdbm)/include" \
GDBM_LIBS="-L$(brew --prefix gdbm)/lib -lgdbm" \
  ../configure \
    --with-pydebug \
    --with-openssl="$(brew --prefix openssl@3.0)" \
    OPT="-g -O0 -Wall"
```

要点:

- 在 `build/` 里执行 `../configure`,即树外构建;`srcdir` 为 `..`。
- `export CC=clang` 用 PATH 里的 **Homebrew LLVM clang**(`/opt/homebrew/opt/llvm/bin/clang`),先用 `command -v clang` 确认。早期环境下它能让 `bear` 正常捕获命令;升级 Bear / LLVM 后仍需验证数据库非空,替代方案见下文。
- `--with-pydebug` 会定义 `Py_DEBUG` 并开启断言/引用追踪。默认 `OPT=-g -Og -Wall`,但 `-Og` 仍保留部分优化（内联、死代码消除等），会导致 LLDB/CodeLLDB 调试时变量被优化掉、单步跳行。因此我们显式传 `OPT="-g -O0 -Wall"` **完全关闭优化**,获得最佳调试体验。
- `--with-openssl` 指向 Homebrew 的 openssl@3.0,保证 `_ssl` / `_hashlib` 能编进去。
- `GDBM_CFLAGS/GDBM_LIBS` 让 `_gdbm` 找到 Homebrew 的 gdbm。
- `PKG_CONFIG_PATH` 优先选择 `tcl-tk@8`,避免默认 Tcl/Tk 9 导致 `_tkinter` 编译失败。

configure 结束后,可在输出里确认 `_ssl`、`_sqlite3`、`_decimal`、`_tkinter`、`_lzma`、`_bz2`、`zlib`、`_gdbm` 等扩展模块都是 `yes`。

## 3. 用 bear 编译并生成 compile_commands.json

```bash
bear -- make -j$(sysctl -n hw.ncpu)
```

产物:

- `build/python` —— 调试版解释器
- `build/compile_commands.json` —— 编译数据库(核心 C 文件,约 260+ 条)

> ⚠️ **bear 只记录这一次 `make` 真正执行的编译命令。** 如果整棵树已经是最新的(`make -q` 返回 0),`make` 什么都不会编,bear 就只抓到 0 条,并把已有的 `compile_commands.json` **覆盖成空的 `[]`**。
>
> 所以要生成完整的数据库,必须在一次**全量编译**中跟踪。若之前已经编过,先清理再跑:
>
> ```bash
> make clean
> bear -- make -j$(sysctl -n hw.ncpu)
> ```

> 另外:早期实测用 Homebrew 的 `clang` 时能正常捕获,Apple 的 `/usr/bin/clang` 或默认 `gcc` 则得到空 `[]`。但升级工具链后仍需检查结果:本次 Bear 4.2.1 + Clang 23.1.0 即使用 Homebrew clang 也得到空数据库,日志解析的替代方案见下文。

## 4. clangd 索引

`compile_commands.json` 留在 `build/` 目录即可。clangd 会从源文件所在目录逐级向上查找,并会检查每一级的 `build/` 子目录,所以 `build/compile_commands.json` 能被自动找到,**不需要**再软链到仓库根。

`build/` 目录本身已被仓库 `.gitignore` 里的 `/build/` 忽略,不会污染 git。

## 5. 验证

```bash
build/python -VV
build/python -c "import ssl, sqlite3, decimal, lzma, bz2, ctypes; print('stdlib c-exts OK')"
```

调试构建可用 `sys.gettotalrefcount` 是否存在来确认 `Py_DEBUG` 已开启:

```bash
build/python -c "import sys; print('Py_DEBUG =', hasattr(sys, 'gettotalrefcount'))"
```

## 日常使用

```bash
# 启动调试版 REPL
build/python

# 用 lldb 调试解释器
lldb build/python

# 改了 C 代码后增量编译(在 build/ 里)
cd build && make -j$(sysctl -n hw.ncpu)
```

- 新增 / 删除源文件后,在 `build/` 里执行 `make clean && bear -- make -j$(sysctl -n hw.ncpu)`,完整刷新 `compile_commands.json`。
- 重新配置(改 configure 选项)时,可在 `build/` 里重跑 `../configure ...`。

## rebase / 升级版本后重新构建

源码版本更新不会自动更新已有的 `build/python`。本次 rebase 到 `v3.11.16` 后,旧解释器仍显示 `3.11.15+`,且 Homebrew LLVM 已从 22 升到 23,因此重新配置并全量编译,同时刷新编译数据库。

在仓库根目录执行(依赖已安装时无需重新 `brew bundle`):

```bash
cd build

CC="$(brew --prefix llvm)/bin/clang" \
PKG_CONFIG_PATH="$(brew --prefix tcl-tk@8)/lib/pkgconfig${PKG_CONFIG_PATH:+:$PKG_CONFIG_PATH}" \
GDBM_CFLAGS="-I$(brew --prefix gdbm)/include" \
GDBM_LIBS="-L$(brew --prefix gdbm)/lib -lgdbm" \
  ../configure \
    --with-pydebug \
    --with-openssl="$(brew --prefix openssl@3.0)" \
    OPT="-g -O0 -Wall"

make clean
# 保留完整日志,并先写临时数据库,检查后再替换旧文件。
bear --output compile_commands.rebuild.json -- make -j$(sysctl -n hw.ncpu) > build.log 2>&1

# 如果拦截结果为空,本机 Bear 4.2.1 支持从日志解析命令。
# 解析不会再次执行编译。
./python -c 'import json; assert json.load(open("compile_commands.rebuild.json"))' || \
  bear parse-sh --input build.log --directory "$PWD" --output compile_commands.rebuild.json
./python -c 'import json; assert json.load(open("compile_commands.rebuild.json"))' && \
  mv compile_commands.rebuild.json compile_commands.json

./python -VV
./python -c 'import sys, sysconfig; print("Py_DEBUG =", sysconfig.get_config_var("Py_DEBUG")); print("OPT =", sysconfig.get_config_var("OPT")); assert hasattr(sys, "gettotalrefcount")'
./python -c 'import ssl, sqlite3, _decimal, lzma, bz2, ctypes, zlib, dbm.gnu, tkinter; print("stdlib c-exts OK")'
./python -c 'import json; db = json.load(open("compile_commands.json")); assert db; print("编译数据库条数:", len(db))'
```

- 先 configure、再 clean/build,让依赖检测和 Makefile 与当前源码及工具链一致;通常不需要 `make distclean` 或删除整个 `build/`。
- 这里把 `OPT="-g -O0 -Wall"` 作为 configure 的参数传入,以便保存进 `CONFIG_ARGS`。旧配置只通过环境变量传入 OPT,没有保存该值,直接 `config.status --recheck` 或由 make 自动重配置时可能回到默认的 `-Og`。
- 显式指定 Homebrew LLVM 的编译器路径,避免 PATH 变化后改用 Apple Clang。`bear` 应跟踪 clean 后的完整编译,避免用增量结果覆盖完整数据库。
- 本次实测默认 pkg-config 选中了 Tcl/Tk 9.0.4,导致 `_tkinter` 报 `Tcl_Size *` 类型不匹配等错误;指定 `tcl-tk@8` 后选择 8.6.18。注意扩展模块构建失败时 make 仍可能返回成功,需检查末尾模块汇总并实际 import 验证。
- `bear parse-sh` 会跳过带命令替换的命令。本次从完整日志解析出 263 条,仅缺 `Modules/getbuildinfo.c`;根据日志补齐该条并展开三个 Git 版本宏后,最终数据库为 264 条。核心解释器、对象和扩展模块的编译参数均已核对。
- `.vscode/launch.json` 仍可使用 `build/python`;当前启动配置没有 `preLaunchTask`,因此 F5 前需先完成编译。源码日常小改动仍可使用上面的增量构建命令。

本次验证:Python 3.11.16、`Py_DEBUG=1`、`OPT=-g -O0 -Wall`;上述扩展模块导入成功,Tcl 为 8.6.18。`test_compile`、`test_dis` 通过(224 个用例,1 个跳过);LLDB 成功命中 `Py_BytesMain`,可读取 `argc` 并继续执行。

## 在 VSCode 里断点调试

命令行 `lldb build/python` 之外,日常更顺手的是在 VSCode 里直接打断点、单步。配置都在 `.vscode/launch.json`。

### 扩展与配置

- 装 **CodeLLDB** 扩展(`vadimcn.vscode-lldb`),Apple Silicon(arm64)上最稳定;`launch.json` 里 `"type": "lldb"` 的配置走的就是它。
- 另有一条 `"type": "cppdbg"` 的备用配置,是给 Microsoft C/C++ 扩展用的,一般用不上。
- 被调试的二进制是树外产物 `build/python`,它会自动定位 `Lib/` 与扩展模块,**无需设 `PYTHONPATH`**。

现成的几条配置:调试当前打开的 `.py` 文件(`${file}`)、交互式解释器(`-i`)、附加到已运行进程(attach),以及下面这条**最常用于源码学习**的「调试 python -c」。

### 用 `inputs` 实现「启动时弹框输入代码」

调试解释器内部时,经常想跑一小段内联代码看它怎么被执行(比如 `1+2`)。与其在 `launch.json` 里写死,不如让 VSCode 启动时弹个框让你现场输入。靠的是 VSCode 的 **`inputs` + `${input:...}` 变量替换**机制:

```jsonc
{
    "name": "(lldb) 调试 python -c <输入代码>",
    "type": "lldb",
    "request": "launch",
    "program": "${workspaceFolder}/build/python",
    "args": ["-c", "${input:pyCode}"],   // 占位符,启动时被替换
    "cwd": "${workspaceFolder}"
}
```

文件末尾、与 `configurations` **同级**处定义这个变量:

```jsonc
"inputs": [
    {
        "id": "pyCode",                  // 与 ${input:pyCode} 靠 id 关联
        "type": "promptString",          // 弹文本输入框
        "description": "要传给 python -c 的代码",
        "default": "1+2"                 // 框里的预填值,可直接回车
    }
]
```

工作原理:

- `${input:pyCode}` 里的 `pyCode` 对应 `inputs` 中 `"id": "pyCode"` 那一项,靠 `id` 关联。
- `F5` 启动时弹框,预填 `default`;你输入的内容原样替换掉 `args` 里的占位符,最终执行 `build/python -c "<你输入的>"`。

`inputs` 支持三种 `type`:

| `type` | 行为 |
|---|---|
| `promptString` | 弹文本框输入(加 `"password": true` 可隐藏输入) |
| `pickString` | 给 `options` 列表下拉选(适合预设几段常用代码) |
| `command` | 取某命令的返回值(如 attach 配置里的 `${command:pickProcess}`) |

> 这套 `inputs` / `${input:...}` 机制是 VSCode 通用的,不限于 lldb——`tasks.json` 里同样能用,可用来做「参数化的构建 / 运行任务」。
