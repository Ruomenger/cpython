# 00. 编译配置

本机(macOS / Apple Silicon)上 CPython 3.11 调试构建的配置:怎么建、为什么这样配、怎么在编辑器里用。

## 一览

| 项 | 值 |
|---|---|
| 构建目录 | `build/`(树外构建,被上游 `.gitignore` 忽略) |
| 解释器 | `build/python` |
| 构建选项 | `--with-pydebug`,`OPT="-g -O0 -Wall"` |
| 编译器 | Homebrew LLVM 的 clang(`$(brew --prefix llvm)/bin/clang`) |
| 编译数据库 | `build/compile_commands.json`(给 clangd 用) |
| 全量重建 | `study/scripts/rebuild.sh`,约 2 分钟 |

## 首次准备

```bash
xcode-select --install              # Xcode Command Line Tools
brew bundle --file=Misc/Brewfile    # 依赖库,和上游 macOS CI 用同一份清单
brew install llvm bear              # 编译器与 clangd、生成编译数据库的工具
```

`Misc/Brewfile` 在 macOS 上装的是 `gdbm`、`mpdecimal`、`openssl@3.0`、`pkg-config`、`tcl-tk@8`、`xz`、`zstd`。

VSCode 需要 clangd 和 CodeLLDB 两个扩展,打开仓库时会按 `.vscode/extensions.json` 提示安装。

## 全量重建

```bash
study/scripts/rebuild.sh
```

脚本依次做四件事,任何一步不对都会报错退出:

1. **configure**:在 `build/` 里执行 `../configure`,输出存到 `build/configure.log`。
2. **make clean**。
3. **全量编译**:在 bear 下执行 make,同时记录编译数据库,输出存到 `build/build.log`。
4. **校验**:编译数据库条数正常才替换旧文件;解释器版本和源码一致;确实是 `Py_DEBUG` + `-O0`;依赖外部库的扩展模块都能 import。

什么时候要跑:

- 第一次构建。
- `study` 分支 rebase 到新标签之后。rebase 不会更新已有的 `build/python`,用下面两条命令比对版本:

  ```bash
  build/python -VV
  grep 'define PY_VERSION ' Include/patchlevel.h
  ```

- Homebrew 升级了 LLVM 或依赖库之后。
- 上游增删了源文件,需要刷新编译数据库时。

跑完在文末「重建记录」加一行。

## 日常使用

```bash
make -C build -j"$(sysctl -n hw.ncpu)"             # 改了 C 代码后增量编译,VSCode 里是 ⇧⌘B
build/python                                       # 调试版 REPL
build/python -m test test_dis                      # 跑某个测试
lldb -s study/scripts/cpython.lldb build/python    # 命令行调试,带 pyo / pybt 两个辅助命令
```

## 为什么这样配

**树外构建。** 所有产物落在 `build/`,源码树保持干净,rebase 时不会被构建产物干扰。

**`--with-pydebug`。** 定义 `Py_DEBUG`,带来这些对读源码有用的东西:

- C 层的 `assert()` 和各种一致性检查生效。
- 自动带上 `Py_REF_DEBUG`:`sys.gettotalrefcount()`、`-X showrefcount` 可用。注意这不是 `Py_TRACE_REFS`,后者要另加 `--with-trace-refs`。
- 内存分配器默认装上调试钩子(相当于 `PYTHONMALLOC=debug`),能查出越界写和释放后使用。
- 编译进逐指令跟踪:模块里定义 `__lltrace__` 之后,此后进入的每个帧都会打印执行的指令和求值栈。
- ABI 标记带 `d`(`libpython3.11d.a`、`*.cpython-311d-darwin.so`)。

**`OPT="-g -O0 -Wall"`,并且写在 configure 的参数里。** 调试构建默认是 `-Og`,仍会内联和消除变量,断点处看不到变量、单步会跳行,所以显式关掉优化。它必须作为 `../configure` 的参数传:这样才会记进 `CONFIG_ARGS`,以后 make 自动触发重新配置时还是 `-O0`;只用环境变量传的话会悄悄回到 `-Og`。

**`CC` 用绝对路径。** 不依赖 PATH 的顺序,避免某天 PATH 变了就换成 Apple 的 `/usr/bin/clang`。

**清掉 shell 里的编译变量。** shell 里如果 export 了 `CPPFLAGS` / `LDFLAGS`(Homebrew 装 keg-only 的包时常提示这么做),configure 会把它们记进 Makefile;而且 Makefile 自己不给这两个变量赋值,每次 make 还会再从环境里读一遍。2026-11-12 就遇到过:shell 里 mysql-client 和 llvm 的路径被带进了所有编译命令。脚本用 `env -u` 把它们清掉,VSCode 的「增量构建」任务也一样。手工 `make` 时如果 shell 里有这些变量,新编译的文件会多带几个 `-I` / `-L`,不影响结果,只是和全量构建的参数不完全一致。

**三个依赖库的指定方式。**

- `--with-openssl="$(brew --prefix openssl@3.0)"`:保证 `_ssl`、`_hashlib` 能编出来。
- `GDBM_CFLAGS` / `GDBM_LIBS`:让 `_gdbm` 找到 Homebrew 的 gdbm。
- `PKG_CONFIG_PATH` 指向 `tcl-tk@8`:默认会选中 Tcl/Tk 9,`_tkinter` 编译报 `Tcl_Size *` 类型不匹配。不需要 `brew link`。

**解释器叫 `python` 而不是 `python.exe`。** 源码在大小写敏感的卷上(`/Volumes/Dev`)。在大小写不敏感的卷上,为了不和源码里的 `Python/` 目录撞名,它会叫 `python.exe`。

## 编译数据库与 clangd

### 怎么生成的

bear 在 macOS 上默认用 wrapper 方式:把 `cc`、`clang` 这些已知名字的编译器换成自己的包装程序来记录命令(preload 方式在开着 SIP 的 macOS 上不可用)。而 CPython 的 Makefile 里 `CC` 是 configure 写死的绝对路径,包装程序顶替不了,所以直接 `bear -- make` 什么都记不到,写出来是空的 `[]`。

脚本的做法是只在生成数据库的那一次 make 上加 `CC=clang`,覆盖 Makefile 里的值,并把 Homebrew LLVM 放到 PATH 最前面。数据库里记下的仍是真实编译器的绝对路径,`Modules/getbuildinfo.c` 这种带命令替换的条目也是展开后的结果。

两点注意:

- bear 只记录这一次 make 真正执行的命令,所以必须是 clean 之后的全量编译。
- **不要手工跑 `bear -- make`**:增量构建或拦截没生效时,它会把好的数据库覆盖成 `[]`。脚本是先写临时文件,条数正常才替换。

备用办法:`bear parse-sh --input build.log --directory "$PWD" --output <文件>` 能从构建日志解析出数据库,但会漏掉 `Modules/getbuildinfo.c`。2026-09-20 把 `CC` 改成绝对路径后拦截就失效了,当时以为是 Bear / Clang 升级导致的,一直用这个办法;2026-11-12 才查清原因。

### clangd 怎么用它

clangd 会从源文件所在目录逐级向上找 `compile_commands.json`,也会看每一级的 `build/` 子目录,所以不需要软链到仓库根。`.vscode/settings.json` 里另外用 `--compile-commands-dir` 明确指了一次。

### 头文件

CPython 的头文件大多不自包含,默认调用方已经 `#include "Python.h"`,单独打开时 clangd 会报一屏 unknown type。仓库根的 `.clangd` 给内部头文件(`Include/internal/*.h`)和 Argument Clinic 生成的头文件(`*/clinic/*.h`)加了 `-include Python.h -DPy_BUILD_CORE`。用 `clangd --check` 实测(clangd 23.1.4),单独打开时有报错的文件数:

| 范围 | 加之前 | 加之后 |
|---|---|---|
| `Include/internal/*.h` | 66 / 68 | 1 / 68 |
| `Objects/clinic/*.h` + `Python/clinic/*.h` | 27 / 27 | 5 / 27 |

剩下的那个内部头文件是 `pycore_parser.h`,它用了 `PyArena` 却没有包含 `pycore_pyarena.h`。

**没解决的:公开头文件**(`Include/*.h`、`Include/cpython/*.h`)单独打开仍然报 unknown type。它们本来就是被 `Python.h` 按固定顺序包含的,同样的办法行不通:带 include guard 的(如 `Include/object.h`)预先包含 `Python.h` 之后,文件自己的内容会被 guard 整个跳过;`Include/cpython/*.h` 没有 guard,会变成重复定义。从 `.c` 文件跳转过去位置是对的,只是文件里有红线、部分悬停不可用。

## 在 VSCode 里调试

配置在 `.vscode/launch.json`,用 CodeLLDB。被调试的是 `build/python`,它自己能找到 `Lib/` 和扩展模块,不需要设 `PYTHONPATH`。

| 配置 | 用途 |
|---|---|
| python -c <输入代码> | 最常用:断点打在 C 代码里,启动时弹框输入一小段 Python |
| python <当前打开的 .py 文件> | 跑当前编辑器里的脚本 |
| python 交互式解释器 | 带 REPL 启动 |
| 附加到正在运行的 build/python | 附加到已有进程 |

几点说明:

- **启动前不会自动编译。** 改过 C 代码先跑「增量构建」任务(⇧⌘B)。
- 用「python <当前打开的 .py 文件>」时焦点要在 `.py` 文件上;焦点在 `.c` 文件时它会把 C 源码当脚本跑。
- 弹框输入靠的是 VSCode 的 `inputs` 机制:`args` 里写 `${input:pyCode}`,文件末尾的 `inputs` 里定义同名 `id` 的 `promptString`。`.vscode/tasks.json` 的「运行测试」任务用的是同一套机制。
- 监视和调试控制台按 C 表达式求值(`lldb.launch.expressions` 设成了 `native`),可以直接写强制转换,例如 `((PyTypeObject *)op->ob_type)->tp_name`。

### 两个辅助命令

`study/scripts/cpython.lldb` 定义了两个命令,VSCode 里自动加载,命令行里用 `lldb -s study/scripts/cpython.lldb build/python`:

| 命令 | 作用 |
|---|---|
| `pyo <表达式>` | 打印一个 `PyObject *` 的地址、引用计数、类型和 repr |
| `pybt` | 打印当前线程的 Python 调用栈 |

它们是在被调试进程里调用解释器自带的 `_PyObject_Dump` 和 `_Py_DumpTraceback`,输出走进程的 stderr:VSCode 里在「终端」面板,不在「调试控制台」。`pyo` 会执行对象的 repr,可能运行 Python 代码,在意现场不被扰动时不要用。

命令行里一次跑完的例子:

```bash
lldb -b -s study/scripts/cpython.lldb \
  -o 'breakpoint set -n list_append' \
  -o 'process launch -- -c "[].append(42)"' \
  -o 'pyo object' -o 'pybt' -o 'bt 5' -o 'kill' \
  build/python
```

启动用 `process launch --` 而不是 `run`:`run` 会对参数做 shell 展开,代码里有 `[]`、`*` 时会失败。

## 已知现象

- **版本串里总带 `-dirty`**(如 `heads/study-dirty`),不代表工作区有改动。Makefile 在 `build/` 里用 `git --git-dir ../.git describe --dirty` 取标签,这时 git 把 `build/` 当成了工作区,树外构建下总会带上。
- **扩展模块编不出来时 make 仍然返回成功。** 要看 `build/build.log` 末尾的模块汇总,或者实际 import 一遍;重建脚本的校验步骤做的就是后者。
